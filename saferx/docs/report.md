## 摘要

多药共用是慢病患者的常态，而药物相互作用（DDI）导致的不良事件中相当比例本可避免。现有在线检查器
以英文为主、按单次 5 药限制使用、且不提供可核查的机制与文献来源。本项目实现了一套中文化的药物
相互作用检查系统 **SafeRx**：以 DDInter 2.0（CC BY-NC-SA 4.0）为知识底座，构建了「1,971 种药 /
234,981 个无序药对」的本地库，配合 366 种常见药的中文名与 5,244 条别名，支持中文 / 英文 / 拼音首字母 /
数据库 ID 四种检索路径。

在核心检查之外，项目补齐了 DDInter 官方仅以网页表格开放的**药物-疾病禁忌（DDSI）、药物-食物
相互作用（DFI）、重复用药**三类数据（8,009 / 805 / 5,663 条），并实现了「药单 × 基础疾病」的
上下文检查与保守风险聚合。NLP 侧在 DDIExtraction 2013 语料上给出三档真实评测：词典法实体
F1 0.656、关键词规则关系 micro-F1 0.602、TF-IDF+LR 关系 micro-F1 0.862，并在 CPU 上完成
BioBERT 微调把实体 F1 提到 **0.877**；预测侧做了 DDI 链接预测实验，补全场景 AUC 0.955、
新药冷启动 AUC 0.747。检索准确性通过 100 条药单与官方检查器自动 A/B 比对验证：**查准率 100%、
查全率 99.64%、分级一致率 100%（824/824）、Major 漏报 0/175**；满规模 20 药单（190 组合）
业务逻辑耗时 9.43 ms（中位）。

关键词：药物相互作用；用药安全；知识库；信息抽取；FastAPI；Vue

## 1 绪论

### 1.1 背景

老年慢病患者常同时服用 5 种以上药物。药物相互作用（Drug-Drug Interaction, DDI）会改变药物的
吸收、分布、代谢或排泄，轻则降低疗效，重则导致出血、心律失常、横纹肌溶解等严重不良事件。
这类风险的特点是**可预测、可预防**：只要在处方/用药环节得到提示，多数事件可以规避。

现实中的障碍不在算法，而在**可得性**：权威数据库（如 DrugBank、Micromedex）多为英文界面且商业授权，
基层与家庭场景难以使用；面向公众的工具往往只给一句「不宜同服」，缺少机制说明与文献出处，
用户无法判断可信度。

### 1.2 目标与范围

本项目定位为**教学与科普工具，不是诊断或处方工具**。据此设定三条设计原则：

1. **可核查**：每条结论都能回溯到数据来源（`source_id`）与参考文献，中文结论与英文原文并置。
2. **诚实边界**：查不到不等于安全。未收录组合、分级未知记录均单独呈现，不并入「安全」。
3. **可离线**：全量数据落本地 SQLite，断网仍可完整演示；前端内置离线降级子集。

### 1.3 主要工作

| # | 工作 | 产出 |
|---|---|---|
| 1 | 数据管道：DDInter CSV → 清洗 → 无序对规范化 → SQLite | 9 张表、45 MB 库、`make data initdb` 一键重建 |
| 2 | 逆向 DDInter 网页表格接口，补齐 DDSI / DFI / 重复用药 | 3 个抓取+清洗脚本，14,477 条新数据入库 |
| 3 | 检查服务与 8 个 REST 接口 | 保守风险聚合、四路径药名归一化、上下文检查 |
| 4 | 六页前端 + 离线降级 + 可打印报告导出 | Vue 3 + Tailwind + ECharts，断网可用 |
| 5 | 两类可复现评测 | 检索准确性 A/B（100 药单）、NLP 抽取（DDIExtraction 2013） |
| 6 | 工程化交付 | 43 个后端用例、数据字典/接口/演示脚本/数据画像、截图兜底 |

## 3 系统需求

### 3.1 功能需求

| 编号 | 需求 | 验收标准 |
|---|---|---|
| F1 | 药名检索与添加 | 中文/英文/拼音/ID 四路径均可命中；未命中给候选而非报错 |
| F2 | 药单两两检查 | n 药给出 C(n,2) 个组合的逐对结论与整体等级 |
| F3 | 上下文检查 | 给定基础疾病时给出药物-疾病禁忌；无上下文时明确提示已跳过 |
| F4 | 食物与重复用药 | 命中酒精/西柚汁等风险；同类别 ≥2 种药给出重复用药告警 |
| F5 | 关系图谱 | 药单子图，节点着色映射最高风险等级 |
| F6 | 报告导出 | 浏览器内生成可打印 HTML，含免责声明与未收录组合 |
| F7 | 文献抽取演示 | 输入中文病例片段，输出药物实体与候选三元组 |
| F8 | 断网可用 | 后端不可达时自动切离线子集，界面标注「演示数据」 |

### 3.2 非功能需求

- **性能**：满规模 20 药单（190 组合）业务逻辑 < 20 ms。
- **可复现**：所有数字可由 `make` 目标重新生成；评测固定随机种子。
- **可解释**：结论必须附带分级、机制与来源三项中的至少两项。
- **鲁棒性**：异常输入不返回 4xx 打断用户（未命中药名走 `unresolved` 通道）。

## 4 系统设计

### 4.1 总体架构

```
Vue 3 SPA (Vite)                        FastAPI (uvicorn)
┌────────────────────┐   /api/*   ┌──────────────────────────────┐
│ views/ 6 页         │ ─────────► │ api/routes/  8 个端点         │
│ stores/ Pinia       │ ◄───────── │ schemas/     Pydantic 契约    │
│ api/client.js       │            │ services/    checker · drug   │
│  └ 失败→api/mock.js │            │              alias · extractor│
└────────────────────┘            │              other_interactions│
                                   │ core/db.py   SQLite 连接池    │
                                   └──────────────┬───────────────┘
                                                  │
                                        data/saferx.sqlite (45 MB)
                                                  ▲
                          pipelines/  download → clean → init_db → profile
```

前后端分离但**同源部署**：生产模式下 FastAPI 直接托管 `frontend/dist`，单进程即可演示，
避免现场起两个服务。

### 4.2 数据模型

9 张表，其中 4 张主数据、3 张扩展数据、2 张辅助：

| 表 | 用途 | 关键约束 |
|---|---|---|
| `drug` | 药品主档 | `ddinter_id` 主键，`name_cn` 可空 |
| `ddi` | 药对相互作用 | `(ddinter_id_a, ddinter_id_b)` 复合唯一，强制 `a < b` |
| `mechanism` | 人工审编中文机制 | 与 `ddi.mechanism_id` 关联 |
| `alias` | 别名（中文/拼音/英文/同义） | `(alias, kind)` 索引 |
| `ddsi` | 药物-疾病禁忌 | 复合索引 `(ddinter_id, disease_en)` |
| `dfi` | 药物-食物 | `(ddinter_id)`、`(food_en)` 索引 |
| `dupli` | 重复用药类别 | `(category_en)` 索引 |
| `template` | 演示模板药单 | 4 套慢病组合 |
| `meta` | 构建元信息 | 9 个键（规模、时间、来源） |

### 4.3 核心检查算法

```
check_meds(meds, diseases):
  1. normalize  每味药经 中文精确 → 英文(忽略大小写) → 拼音首字母 → ID 四路径归一化
                未命中者进 unresolved[]，附候选（编辑距离 Top3）
  2. dedupe     归一化后按 ddinter_id 去重，保持输入顺序
  3. pairs      枚举 C(n,2) 组合，按 (min_id, max_id) 查 ddi 表
                 命中 → 记录 level / mechanism_en / mechanism_cn / management / source_id
                 未命中 → 进 unrecorded_pairs[]（显式呈现，不视为安全）
  4. context    diseases 非空时查 ddsi；恒查 dfi 与 dupli
  5. aggregate  分级计数 → summary.overall：含 Major→red，含 Moderate→orange，
                 仅 Minor→green，无记录或仅 Unknown→gray
                 overall_all = 取 DDI 与三类上下文中的最高等级（保守聚合）
  6. notes      coverage_note：全命中 / 部分未收录 / 仅分级未知，三种文案
```

两条刻意的设计选择：

- **保守聚合**：任一类别判 `red` 则整体 `red`。对用药安全而言，漏报的代价远高于高报。
- **未收录单列**：`unrecorded_pairs` 与 `pairs` 结构隔离，前端用不同样式展示，避免用户把
  「无记录」读成「没问题」。

### 4.4 药名归一化

拼音首字母是中文场景的必要补充（用户常打 `hfl` 而非「华法林」），但天然有冲突（如 `klms` 可对应
多个药名）。处理策略：冲突项**不做映射**，提示改用中文全名——宁可让用户多打两个字，也不猜。

## 5 实现要点

### 5.1 后端分层

`routes`（HTTP 契约与参数校验）→ `schemas`（Pydantic 模型）→ `services`（业务逻辑，不依赖 FastAPI）
→ `core/db.py`（连接管理）。好处是 `services.checker.check_meds()` 可被评测脚本直接调用，
A/B 比对测的是业务逻辑本身而非 HTTP 开销（`pipelines/eval_accuracy.py` 即如此）。

### 5.2 数据管道

四条独立管道，均带「快照 + 校验」：

1. **DDI 主库**：14 个分类 CSV → 无序对规范化 → 冲突取最高级 → 复合唯一索引去重。
2. **其他三类**：DDInter 未提供 CSV，逆向其 Django DataTables 接口（需 CSRF token、分页 POST、
   每页 500 条）→ 落盘 JSONL 快照 → 清洗归位字段语义 → 过滤指向库外药品的记录。
   原始 8,359 / 857 / 6,033 条，清洗后 8,009 / 805 / 5,663 条（丢弃率 4.2% / 6.1% / 6.1%）。
3. **别名表**：人工审编 366 种常见药 → `pypinyin` 生成首字母 → 检测冲突项。
4. **画像与评测**：`profile_data.py` / `eval_*.py` 直接读库，图表与正文同源，重跑即更新。

### 5.3 前端

Vue 3 组合式 API + Pinia。`api/client.js` 带 2 秒超时，失败即透明切换到 `api/mock.js`
（28 药 / 21 关系 / 6 种疾病占位），并在顶部显示「演示数据」标记——答辩现场断网不致翻车。
结果页的「其他相互作用」用统一的 `OtherRiskCard`（左侧色条 + 分级徽章 + 可折叠英文原文），
三处复用。

### 5.4 NLP 基线

`services/extractor.py` 采用词典最长匹配 + 句内共现 + 关键词打分，输出实体与候选三元组；
其中 `status=known` 的三元组会回查主库并附上真实分级，`status=new` 的作为候选取样供人工评审。
这条「规则基线」的价值不在准确率，而在**可解释、零依赖、离线可跑**，且其水平已被量化
（见 §8.3），后续换模型时有了对照基线。

## 6 数据工程中的四个具体问题

### 6.1 无序对导致的重复计数

DDInter 按药理分类分文件存放，同一药对会在多个文件重复出现，且方向不固定（A-B 与 B-A 各出现一次）。
若直接入库，同一组合会查出两条记录甚至给出不同分级。解决：入库前统一为
`(min(id_a, id_b), max(id_b))` 并建复合唯一索引；分级冲突时保留最高级。规范化后 234,981 个唯一药对，
零重复。

### 6.2 无 CSV 时的抓取

DDInter 首页只暴露 `/server/dis_food/` 与 `/server/other_interaction/` 两个页面入口，表格由
DataTables 以 serverSide 模式异步加载。抓取流程：GET 页面取 `csrfmiddlewaretoken` →
`POST /server/{disease,food,dupli}-interaction-source/` 分页取数（每页 500、间隔 0.6 s）→
写入 JSONL 快照。三类的总条数与官方页面宣称完全一致（8,359 / 857 / 6,033），可交叉验证抓取完整性。
脚本支持 `--offline`（仅校验缓存）与 `--force`，答辩环境无网络时不影响复现。

### 6.3 源字段语义错位

DFI 接口把「机制」字段命名为 `magnesium`（镁），实际内容是 `Absorption / Metabolism / Synergy /
Antagonism / Excretion / Distribution / Others` 七类机制标签。若照字段名直译入库，会在前端显示
「机制：镁」这类荒谬结论。处理：清洗时按值域判定语义并归位为 `mechanism_en`，同时把中文映射写入
`mechanism_cn`。这类问题无法靠 schema 校验发现，只能靠**看过数据**。

### 6.4 索引与查询计划（性能工程）

`ddsi` 表 8,009 行但每行带 1–3 KB 的英文描述，总 15 MB。初版按 `disease_en` 建单列索引，
SQLite 在 `IN` 列表变长时会选择「疾病优先」计划：先取出某病名下 641 行带长文本的记录，再按药过滤。
10 药场景实测 6.7 ms。改为复合索引 `(ddinter_id, disease_en)` 并在 SQL 中显式 `INDEXED BY`
固定计划后降到 0.09 ms（**22 倍**）。反之，疾病选择器需要按疾病聚合计数，若走复合索引则要回表读
大文本（17.4 ms），故另建覆盖索引 `(disease_en, disease_cn, level)`，降到 1.3 ms。

结论：**同一个表的最优索引取决于访问模式，不能只按「哪个列有 WHERE」决定**；且当统计信息不足以
稳定计划时，显式提示比反复 `ANALYZE` 更可控。

## 7 界面与交互（简述）

六页：首页（规模与能力概览，数字来自 `/api/health`）→ 用药清单（检索、模板、疾病选择）→
检查结果（分级卡、机制折叠、其他相互作用三段、未收录组合、导出）→ 关系图谱（ECharts 力导向，
线宽映射等级）→ AI 实验室（文献抽取演示）→ 关于（数据来源、覆盖边界、免责）。

视觉上以「风险色」为主轴（红/橙/绿/灰四档），左侧色条 + 分级徽章保证色盲用户也能靠文字区分；
英文原文默认折叠，避免长文本淹没结论。截图见 `deploy/screenshots/`。

## 8 实验与评估

本章对应方案 §8 的六项评估。所有实验在本机完成（Windows 11 / Python 3.13 / SQLite 3 /
Vue 3.5 + Vite 6），脚本与原始输出随仓库提交。

### 8.1 数据画像

数据画像回答「这套库长什么样、能支撑什么结论」。完整图文见 `docs/data_profile.md`。

**(1) 总体规模**

| 指标 | 数值 |
|---|---|
| 药物 | 1,971 种 |
| 唯一药对 | 234,981 对 |
| 中文通用名覆盖 | 366 种（18.6%） |
| 别名 | 5,244 条（中文 367 / 拼音 361 / 英文 4,458 / 同义 58） |
| 人工审编中文机制 | 21 条 |

**(2) 风险分级分布**

| 分级 | 药对数 | 占比 |
|---|---|---|
| 严重 Major | 39,082 | 16.63% |
| 中度 Moderate | 143,748 | 61.17% |
| 轻微 Minor | 9,736 | 4.14% |
| 分级未知 Unknown | 42,415 | 18.05% |

Moderate 占六成符合审编库「宁可高报不漏报」的收录倾向。真正值得注意的是 **18.05% 的记录官方未标
严重度**——若把 Unknown 并入「安全」，等于凭空消除近五分之一的风险信号，因此系统将其独立展示为
「分级未知」。

**(3) 高连接度药物 Top 5**

| 药物 | 关联药对 | 其中 Major |
|---|---|---|
| 西酞普兰 Citalopram | 919 | 263 |
| 地塞米松 Dexamethasone | 910 | 106 |
| 氯氮平 Clozapine | 889 | 417 |
| 卡马西平 Carbamazepine | 882 | 185 |
| 苯妥英 Phenytoin | 882 | 177 |

连接度最高的不是「毒性最大」的药，而是 **CYP450 代谢枢纽与治疗窗窄的药物**（华法林列第 7，
864 对）。这解释了产品设计的取向：单药查询价值有限，**药单整体检查**才能捕捉枢纽节点带来的
连锁风险。

**(4) 其他相互作用三类（本项目新增入库）**

| 类别 | 入库条目 | 覆盖 | 分级（Major / Moderate / Minor） |
|---|---|---|---|
| DDSI 药物-疾病禁忌 | 8,009 | 459 种疾病 × 1,391 种药 | 3,570 / 4,359 / 80 |
| DFI 药物-食物 | 805 | 29 类食物 × 680 种药 | 92 / 677 / 36 |
| 重复用药 | 5,663 | 95 个治疗类别 × 649 种药 | 不分级 |

分布上有两个可解释的集中：疾病侧「肾脏疾病 / 肝脏疾病」条目最多（641 / 638），与药代动力学
常识一致；食物侧酒精（433）与西柚汁（137）合计占 70.8%，正是 CYP3A4 抑制与中枢抑制叠加的
真实临床关注点。重复用药条目最多的是抗组胺药（1,613）与非甾体抗炎药（867）——恰是感冒药、
止痛药里最容易「一药多名、重复服用」的品类。

### 8.2 检索准确性

**目标**：验证「抓取—清洗—聚合—查询」链路是否正确，量化与官方检查器的一致性。

**方法**（`pipelines/eval_accuracy.py`，固定种子 20261107）：

1. 从库内按 DDI 度数取前 260 种药作为近似「临床常用药池」，随机抽 **100 条药单**，每条 5 种药
   （官方检查器上限 5 药/次），共 **827 个药对**。
2. 官方侧：`POST https://ddinter2.scbdd.com/checker/`，提交 DDInter ID，解析逐对 severity。
3. 本地侧：直接调用 `services.checker.check_meds()`（不经 HTTP）。
4. 逐对比较药对集合与分级，统计查准/查全/分级一致/Major 漏报/耗时。

**结果**

| 指标 | 数值 | 说明 |
|---|---|---|
| 官方命中药对 | 827 | — |
| 本地返回药对 | 824 | — |
| 查准率 Precision | **100.00%** | 本地返回的药对官方全部返回（无臆造） |
| 查全率 Recall | **99.64%** | 827 中缺 3 |
| 分级完全一致率 | **100.00%** | 824/824，严重度完全对齐 |
| 药对集合完全一致的药单 | 97/100 | 其余 3 条各缺 1 对 |
| Major 漏报 | **0 / 175** | 最高风险等级零漏报 |
| 本地耗时 | 中位 1.86 ms / P95 2.83 ms | 单条 5 药药单 10 对 |
| 官方请求失败 | 0 | — |

**3 条缺失药对**为 `Apalutamide+Clopidogrel`、`Celecoxib+Fosphenytoin`、`Phenelzine+Quinidine`：
官方网页库相对其 CSV 快照存在增量更新。系统按快照说话，这类差异会被明确记录而非隐藏。

**诚实边界**：两侧同源于 DDInter 2.0，高一致率只能证明**工程链路正确**，不能据此声称临床准确性。
同源验证是这类评测的固有局限，须在结论中写明。独立验证应由药学人员取说明书/指南明确记载的
20~30 组相互作用做人工对照。

### 8.3 NLP 抽取评测

**语料**：DDIExtraction 2013（BRAT 标注），Train 714 篇 / Test 303 篇。词典由 `drug` +
`alias(en|synonym)` 去重得 2,042 条英文药名。句内共现候选药对 5,994 条，其中人工标注为相互作用
**862 条**。

**结果一：实体识别**

| 方案 | P | R | F1 | 匹配口径 |
|---|---|---|---|---|
| 词典最长匹配 | 0.934 | 0.506 | **0.656** | char span 精确匹配 |
| **BioBERT 微调** | **0.872** | **0.882** | **0.877** | token 级 BIO 实体匹配 |

词典法 Precision 高而 Recall 低，原因是语料中的**商品名、缩写、实验化合物（DRUG_N）大量不在
DDInter 词典内**——这正是「词典法 vs 序列标注模型」的核心差距。BioBERT 把 Recall 从 0.506 拉到
0.882，F1 提升 22 个百分点。分类型看 DRUG 0.923 / BRAND 0.915 / GROUP 0.867，最弱的仍是
DRUG_N（F1 0.385，训练样本仅百余条，类别极不平衡）。

> 口径差异须说明：两行的匹配粒度不同（char span vs token BIO），后者对边界更宽松，
> 因此只能作**趋势对比**，不能表述为「提升 34%」这类精确倍数。

BioBERT 训练配置：`dmis-lab/biobert-base-cased-v1.2` 骨干，3 epoch / batch 16 / lr 3e-5 /
max_len 128，**纯 CPU 73.3 分钟**，train 7,231 句 / test 2,230 句。产物在 `ml/artifacts/biobert-ner/`，
完整报告见 `docs/eval_ner_biobert.md`，复现命令 `python ml/train_ner.py --epochs 3`。
单 seed 单次运行、未做超参搜索，数字应视为该骨干在此语料上的**下界**。

**结果二：关系四分类**（仅对 gold 药对，四类 MECHANISM / EFFECT / ADVISE / INT）

| 方案 | micro-F1 | macro-F1 | 说明 |
|---|---|---|---|
| A. 关键词规则基线 | 0.602 | 0.547 | 无训练，机制/效应/建议关键词打分 |
| B. TF-IDF + 逻辑回归 | **0.862** | 0.790 | char 2–4gram，训练 3,651 条 |
| C. BioBERT + 分类头 | 未执行 | — | 见 §10 后续工作；实体侧已验证可行 |

分类型看，规则基线在 MECHANISM（0.566）与 INT（0.308）上最弱，TF-IDF+LR 分别提升到 0.909 和
0.519；INT（"no interaction"）依赖否定与语境，特征最稀疏，两种方法都难。
C 档未做关系分类（只做了实体识别），原因是关系分类的瓶颈已被证明在实体而非分类器（见解读 2），
先把实体做对收益更大。

**四点必须说明的解读**：

1. 0.862 是**偏乐观**的数字：只取 gold 实体对、不含负例检测，且 DrugBank 句式高度模板化
   （"may increase the risk of…"），char n-gram 足以捕获。文献中 BERT 类模型在该语料报告
   0.75~0.86，差异主要来自评测设置而非模型优劣，**不能据此宣称小模型胜过 BioBERT**。
2. 真实差距在**端到端**：词典实体 F1 只有 0.656，端到端必然显著低于 0.862。BioBERT 把实体
   F1 提到 0.877 后，端到端的瓶颈才真正回到关系分类与同义归一化上。
3. 重复检查：测试集与训练集完全相同的掩码句子占 **6.1%**，剔除后 micro-F1 为 0.864，
   与全量基本一致，说明结果不是靠句子重复刷出来的。
4. **BioBERT 只做了实体、未做关系分类**：这是有意取舍。关系分类的输入是 gold 药对，
   分类器已接近模板化数据的上限；而实体召回 0.506 会让真实场景下大量药对**根本没被识别进来**。
   把有限的 CPU 算力先投给实体，收益最大。

### 8.4 预测实验（链接预测）

方案原定 DDIMDL：用药物 SMILES、靶点、酶/转运体等**结构特征**做多模态深度预测，需要 GPU。
但 DDInter 数据**不含 SMILES、靶点、ATC**（实测 `atc_code` 覆盖 0 条），无法复现该模型。
与其虚构一个数字，改做一个能在此数据上真实完成的问题：

> 只用药物的**图结构位置与治疗类别**，能否预测一对药之间是否会有相互作用记录？

这是链接预测，不是 DDIMDL。它能回答一个对本项目更实际的问题：**这套系统能不能自动扩库**。

**协议**：正样本 20,000 条库内药对，负样本 20,000 条库内不存在的药对；19 维特征分三组
（拓扑 12 维、治疗类别 4 维、风险画像 3 维）；两种划分——A 随机边 8:2（补全已有药物的缺失记录）、
B 按药遮 5%（新药冷启动，5 轮重复取均值）。

| 设置 | 特征 | AUC | AUPRC | P@1000 |
|---|---|---|---|---|
| A 补全 | 拓扑 12 维 | 0.9542 | 0.9524 | 0.994 |
| A 补全 | 拓扑 + 类别 + 画像 19 维 | **0.9547** | 0.9528 | 0.993 |
| B 冷启动 | 拓扑 12 维 | 0.5127 ± 0.0288 | 0.5196 | 0.495 |
| B 冷启动 | **仅类别 + 画像 7 维** | **0.7473 ± 0.0112** | 0.7442 | 0.850 |
| B 冷启动 | 拓扑 + 类别 + 画像 19 维 | 0.4913 ± 0.0603 | 0.4977 | 0.501 |

**三个结论**：

1. **补全场景能力很强**（AUC 0.955）。置换法显示 Resource Allocation 单特征贡献 +0.437 AUC，
   是绝对主力——这与数据画像里「DDI 高度集中在代谢枢纽药物周围」互相印证。
2. **冷启动下拓扑特征是"毒药"**：AUC 0.513 在随机线附近大幅摆动。被遮住的药在训练图中孤立，
   邻居特征恒为 0，而训练集里"特征全零"的样本几乎都是负例，模型于是学到"全零即负例"。
3. **冷启动应关掉拓扑、改用画像**：只用 7 维类别的 AUC 0.747，比纯拓扑高 0.235 且方差小得多；
   两者混用反被拉回 0.491。工程含义明确：**新药入库走「类别 + 禁忌 + 食物」通道，不走图通道**。

这也是线上系统把 `status=new` 一律标为「候选，需人工核实」、不做自动入库的依据。
完整报告见 `docs/eval_prediction.md`，复现 `python pipelines/eval_link_pred.py --n 20000`。

**(5) 并发压测与一个被压出来的真实缺陷**

单请求快不代表扛得住并发。对线上实例做并发梯度压测（20 药满规模 `/api/check`）时出现约
10% 的 500，响应体仅 21 字节且**比成功请求更快返回**——说明是快速失败而非超时。抓取异常栈后
定位到：

```
sqlite3.ProgrammingError: SQLite objects created in a thread can only be used
in that same thread. The object was created in thread id 41144 and this is
thread id 14172.
```

根因不在 SQLite，而在依赖调度：FastAPI 对「同步生成器依赖」的处理是把
`__enter__`、端点执行、`__exit__` 三段分别提交给线程池，并发一高、线程池被打满时，这三段
会落在**不同线程**上；而 Python 的 `sqlite3` 默认禁止连接跨线程使用。低并发时线程池空闲、
三段恰好命中同一线程，因此这个 bug 在功能测试与低并发手工测试中从未暴露。

修复为 `sqlite3.connect(..., check_same_thread=False)`。这样做是安全的：连接仍是「每请求独占、
请求内顺序使用」，任何时刻只有一个线程在用同一个连接；底层 SQLite 以 serialized 模式编译，
自身线程安全。同时补两条回归测试（跨线程查询 + 跨线程关闭），锁死该行为。

| 并发数 | 修复前 | 修复后 |
|---|---|---|
| 16 | 80 次请求中 **53 次 500** | **0 次失败** |
| 32 | — | 32/32 通过，中位 0.86 s |
| 48 | — | 48/48 通过，中位 1.17 s |

这件事的教训比数字更重要：**功能测试全绿 + 单请求毫秒级，仍然可能在高并发下大面积失败**；
并发问题必须靠并发测试去逼，靠阅读代码或单线程测试是看不出来的。

## 9 讨论

### 9.1 有效性威胁

| 威胁 | 影响 | 当前处理 |
|---|---|---|
| 同源验证 | 一致性高不等于临床准确 | 明确写入结论与页面文案 |
| 中文名覆盖仅 18.6% | 1,605 种药只能用英文名检索 | 界面提示，支持英文/拼音兜底 |
| 机制中文仅 21 条 | 多数药对只有英文原文 | 折叠展示原文，不臆造翻译 |
| 分级口径随来源变化 | #4/#7 与方案预期不同 | 忠实呈现源分级 + 机制原文 |
| NLP 未做端到端 | 0.862 高估实际可用性 | 单列实体 F1（词典 0.656 / BioBERT 0.877）说明瓶颈 |
| 实体 F1 两档口径不同 | char span vs token BIO 不可直接相减 | 报告中标注为趋势对比，不给精确倍数 |
| 链接预测负例是"未记录" | 高估 AUC | 明确写入 `eval_prediction.md` 局限段 |
| 单机部署，无横向扩展 | 并发天花板受单进程限制 | 已做 48 并发压测（全 200，中位 1.17 s）；定位为教学/演示，不做生产容量承诺 |

### 9.2 与原始方案的偏差

| 方案条目 | 计划 | 实际 | 原因 |
|---|---|---|---|
| DDSI/DFI/重复用药 | 换源自建或 CMeKG | 逆向官方网页接口抓取 | 官方确有数据，只是没给 CSV；自建规则精度不可控 |
| 检索准确性 | 人工比对 | 自动 A/B + 差异明细 | 找到官方 `POST /checker/`，可 100 条规模化，且可复现 |
| NLP 三行对比 | BioBERT / UIE / 规则 | 词典 + 规则 + TF-IDF+LR + BioBERT 四行 | 装好 CPU 版 PyTorch 后实际完成微调，实体 F1 0.877 |
| 预测实验 | DDIMDL | 改为链接预测 | 数据无 SMILES/靶点/ATC，DDIMDL 不可复现；链接预测能在此数据上真实完成 |

这些偏差都写进了页面「关于」与文档，不做模糊表述。

## 10 结论与展望

### 10.1 结论

1. **知识库可行且够用**：DDInter 2.0 提供 234,981 个药对，加上三类上下文数据共 14,477 条，
   足以支撑面向公众的用药提醒场景；瓶颈不在数据量而在中文表达层的覆盖。
2. **工程链路可验证**：与官方检查器 100 条药单 A/B，查准 100% / 查全 99.64% / 分级一致 100% /
   Major 漏报 0，且 3 条差异可逐条解释。
3. **诚实设计有代价但值得**：Unknown 独立展示、未收录组合单列、不做推测性翻译——短期看界面
   更「啰嗦」，长期看是这类工具唯一站得住的姿态。
4. **性能不是问题**：满规模 20 药单业务逻辑 9.43 ms，瓶颈在响应体积而非计算；索引与查询计划的
   实测差异达 22 倍，说明「按访问模式设计索引」比「给所有 WHERE 列加索引」更有效。

### 10.2 展望

1. **NLP 从实体走向端到端**：实体识别已在 CPU 上做到 F1 0.877，下一步是把 BioBERT 实体 +
   关系分类串成端到端流水线，处理真实说明书文本（而非 gold 药对），这才是抽取模块的实用形态。
2. **中文机制文本规模化**：当前 21 条靠人工审编。可行路径是「英中对照句对 + 术语约束的机器翻译 +
   药师抽检」，并把审编入口做成可提交的评审队列。
3. **别名表继续扩张**：从 366 向 800 种推进，优先覆盖基层常见药与中成药通用名。
4. **结构化说明书接入**：DDSI/DFI 的数据源粒度仍偏粗（29 类食物），接入药品说明书可细化到
   「具体食物×具体制剂」。
5. **冷启动扩库走画像通道**：链接预测实验已证明新药不应走图通道（AUC 0.513），而应走
   「治疗类别 + 禁忌 + 食物」通道（AUC 0.747）。这条结论可直接指导后续的候选挖掘策略。
